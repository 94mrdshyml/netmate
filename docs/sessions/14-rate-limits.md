# 14. Rate limits for sign-in and sign-up (2026-10-23)
- Branch / PR: feat/rate-limits
- Done: the exact D1 limiter from PRD 8.11. New table `rate_hits` (migration `0002_rate_hits`, additive, forward-only). `takeSlot` checks and records in one SQL statement (`insert ... select ... where count < max`), so simultaneous requests cannot both take the last slot; a refused attempt is not recorded, so waiting is enough and hammering never extends the wait. Keys are a label plus a salted SHA-256 of the IP, email or link id (salt is `AUTH_SECRET`), never the raw value. Limits: sign-in 30 per 10 minutes per IP and 10 per 10 minutes per email; sign-up 10 per 10 minutes per IP and 20 per 10 minutes per invite link (the PRD said only "also limited", so the number is a decision). Sign-in and sign-up actions apply them and show "Too many attempts. Try again in N minutes." `pruneRateHits` deletes old rows. The deploy-job smoke test was fixed first in PR #29 (it expected Home for a signed-out visitor), and PR #28's deploy is confirmed live and green.
- Tests: 16 new integration (max then refuse, refused not recorded, exact retry time, window slides, people and limits kept apart, email case-insensitive, **25 simultaneous requests give exactly 5 slots**, only hashes stored, salt matters, each PRD limit, IP helper, wording, pruning) and 2 new e2e (11th wrong sign-in for one email refused with a wait time; 11th sign-up try from one address refused).
- Decisions: the visitor's address is `cf-connecting-ip` (Cloudflare overwrites it in production); missing header shares one "unknown" bucket (local use only). e2e visitors set their own address header so limits never trip across tests. Sign-up per link is 20 per 10 minutes.
- Open: the daily cron that calls `pruneRateHits` does not exist yet (table growth is tiny until then); "any request to the auth service" (60 per 10 minutes per IP) and username-availability limits arrive with the features they guard; password-check and email-send limits arrive with settings and Resend.
