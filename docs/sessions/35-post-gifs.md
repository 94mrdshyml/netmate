# 35. GIFs on posts (2026-10-23)
- Branch / PR: feat/post-gifs, PR below once opened. Second of the two PRs the owner asked for (place was session 34). Opened only after the place PR was merged.
- Done: a "GIF" button in the composer (posts and replies) opens a search box ("Search KLIPY", trending first, results in Klipy's order, "More GIFs", "Powered by KLIPY"). One GIF per post, never with photos, can stand alone. A post shows the GIF under its words in lists, on the post page, in search results and in replies. The admin saves the Klipy key on `/hq/services` (GIF search card); removing it turns GIF search off and hides the button, GIFs already on posts still show.
- How: the member's phone asks Klipy directly (owner's choice, session 34, see below). `src/lib/gif.ts` holds the rules: only https addresses on `static.klipy.com`, `static1`, `static2`, ending in .gif or .webp, no login or port, no look-alike hosts; sizes 1 to 4096; title cleaned and cut at 140; it also reads Klipy's answer (`parseKlipyPage`, skips what it cannot use, never reorders) and builds the request (`klipyUrl`: key in the path as Klipy designed it, 24 per page, content filter "medium", gif and webp only, no member id). `post_gifs` table (migration `0012_post_gifs.sql`, new table so its CHECKs are in CREATE TABLE: host, size, title). `createPost` takes a 7th argument (the GIF) and writes the row in the same `db.batch()` as the post; refuses `bad_gif` and `gif_with_photos`. `src/server/gifs.ts`: `readKlipyKey` (only while GIF search is on and the key decrypts), `saveKlipyKey` (key and "on" in one batch), `removeKlipyKey`, `gifPanel`. The admin's browser tries a new key with Klipy before saving (Klipy wants every request from a browser); the server then checks its shape and stores it encrypted.
- Owner decision (session 34): "Phone talks to Klipy". Klipy puts the key in the search address and requires searches and pictures to come from the member's browser, so the key goes to signed-in members' browsers while GIF search is on. `CLAUDE.md` rule 3 now says so (and that the Resend key never goes to a browser); PRD 8.2, 10 and 13 updated. The key is never logged, never emailed, never shown back in `/hq`, never given to a signed-out visitor. GIF requests carry no cookies and no referrer; pictures load with no referrer.

The browser tests never reach Klipy: Playwright answers its API and picture hosts.
