# 45. Demo data on a real site, from /hq/demo (2026-10-24)
- Branch / PR: feat/demo-in-hq. The owner ran `bun run db:seed` on their own computer, got "no admin yet" (their local database was empty), and said they want to see the demo on netmate.mridu.workers.dev.
- Conflict, asked and answered: CLAUDE.md said fake data stays out of a real instance and production changes are CI-only. I asked; the owner chose "on the real site anyway" over a separate demo site or local only. So the rule is now changed on purpose: one exception, the admin's own page. `CLAUDE.md` and PRD (decision 18) say so. I did not run anything against the live site and cannot: the work is a button the owner presses, inside the deployed app.
- How: the demo code moved from `scripts/demo/` to `src/demo/` so the app can use it. `/hq/demo` (admin only, 404 for anyone else, checked on the server for every call) has "Add demo people" and "Remove demo data" (asked twice).
- Steps: one request on Cloudflare may make about 1000 calls to the database and storage; the whole demo needs about 1500 (every like, follow and picture is a call). So adding runs as 7 steps, one request each, driven by the page: the people and follows, then the posts in chunks of 20 with their likes, saves, reposts and dates, then the finishing touch. Each step can be run again without making anything twice (people are found by their email, posts by author and words), so a step that failed can be carried on by pressing the button again. In the browser the whole thing takes about 8 seconds locally.
- No sign-in: on a real site the demo people have no password record at all, so nobody can sign in as them. (On a local database `bun run db:seed` still gives them the password `demo-password`.) This removes the main danger of fake accounts on an invite-only site.
- Removing: deletes every person who has an email ending in demo.example.com AND one of the 14 demo usernames (the database cascades to posts, replies, tags, mentions, GIFs, cards, likes, saves, reposts, follows, requests and alerts), deletes their pictures from storage, then counts likes, replies and reposts again on every post that stays. A reply a real member wrote to a demo post is deleted with the post (a reply cannot outlive its post); the page says so.
- Tests: unit (names unique per person, as before); integration (`demo-seed.test.ts`, 15): the steps run twice change nothing, steps out of range are refused, status counts, removal leaves the database as it was (rows, pictures, search, feed, the admin's own post counts), removing nothing is fine, adding in steps with no password gives people who cannot sign in. Browser (`zz-demo-data.spec.ts`, runs last): a stranger gets 404; the admin adds, sees a demo profile and search results, removes in a `finally`, and the profile is 404 again.
- Not done: scheduled reset of a demo instance (PRD phase 7); a demo marker column (people are found by their email domain together with their username, so a real member is never matched).
- Heads-up for the owner: while the demo is on, real members see the 14 people and about 90 posts. Remove it before inviting anyone.
