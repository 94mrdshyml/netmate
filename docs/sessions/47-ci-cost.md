# 47. CI cost: from about 16 billed minutes a push to about 10 (2026-10-24)
- Branch / PR: chore/ci-cost. The owner ran out of the 2000 free GitHub Actions minutes, and the deploy of PR 68 failed to start (a job that dies in one second with no log is what an empty allowance looks like; my first advice, to re-run it, could not work).
- Where the time went (measured, not guessed): a full local browser run was 5.3 minutes, and four tests took exactly 66 seconds each. They waited 61 seconds inside `sendPost` for the post limit (10 a minute per person) to reset, because the whole suite shares one admin who posts from many files. That was 4.4 minutes of sleeping. On GitHub the browser job took 8 minutes 13 seconds, which also included a second full build of the app (about 1.5 minutes) that the build job had already done. Every push billed about 16 minutes (type and unit checks 3, browser tests 9, build 1, three small checks 3), and a merge to main repeated all of it on code the pull request had already tested.
- Done (all four options the owner chose):
  1. No more sleeping: each browser test counts its own posts apart (`tests/e2e/fixtures.ts` sets a cookie per test; the server uses it only when `ENV` is exactly `test`, via `postSubject` in `src/server/rate-limit.ts`). The real limit is unchanged and is now tested directly (it was only ever tested by accident): ten posts, the eleventh refused with a wait, the minute passing, people counted apart, and proof that any other `ENV` ignores the scope. `rate-limit.spec.ts` and `setup.spec.ts` keep Playwright's own `test`.
  2. One build per run: the build job saves `.open-next` to the cache, the browser job restores it and skips its own build; if the cache misses it builds itself as before.
  3. Documentation-only pushes (everything under `docs/`, any `.md`, `LICENSE`) skip the slow jobs and are not deployed. `scripts/ci/changes.sh` decides; it is tested in a throwaway git repo (`tests/unit/ci-changes.test.ts`), and any doubt (an unknown commit, a first push with no main to compare with, no changed files, a manual run) runs everything.
  4. After a merge to main the unit, integration and browser tests do not run again; the deploy job builds the app itself (a type or build error stops it before anything is uploaded) and still waits for the sign-off, audit and secret scan. A failure anywhere still blocks the deploy.
- Result, measured locally: the browser suite went from 5.3 to 3.3 minutes and the slowest test from 66 to 14 seconds. The estimate for GitHub (not yet measured, there are no minutes to run it): the browser job from 8 to about 3 minutes, a code push from about 16 to about 10 billed minutes, a documentation-only push to about 3, and a merge to main from about 19 to about 6. My first estimate of "about 5 a push" was too optimistic: the type and unit checks (3 minutes) and the three small jobs (a minute each, rounded up) remain.
- Not done, owner's call: folding the sign-off, audit and secret scan into one job would save two more billed minutes a push but renames required checks; making the repository public makes the minutes free; a spending limit or payment method on GitHub removes the problem; and the browser job could run in two halves in parallel (faster, but the same minutes).
- Rule for future sessions: CLAUDE.md now says to run everything locally and push once per change, and never to add a wait for a rate limit to a browser test.
