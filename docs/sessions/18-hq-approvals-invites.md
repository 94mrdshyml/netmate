# 18. /hq: approvals and invites (2026-10-23)
- Branch / PR: feat/hq-approvals-invites
- Before this: PR #34 (avatars and covers) is live, deploy green. The owner asked to start `/hq`.
- Scope decision: `/hq` is split into PRs. This one is the admin shell, Approvals and Invites (the missing capability: Pending people could not be approved). Branding (name, logo, favicon, colour, radius, font, avatar style, live preview) and Email (Resend key, test send) are separate later PRs.
- Done: `requireAdmin()` (`src/auth/admin.ts`) returns the admin or 404s; the `/hq` layout, every page and every action call it, so a member or a signed-out visitor sees a plain 404, never a redirect or 403. Wide layout (only the panel; stacks on a phone, no sideways scroll). Pages: Overview (members, waiting), Approvals (oldest first; name, username, email, time, whose link; Approve; Reject asks "Yes, reject" first), Invites (set automatic approvals per member link 0 to 1000; every active link with its owner, count and copy button; "Make a new link" asks first). Settings gets an "Admin panel" row for the admin only. `src/server/admin.ts` holds the logic.
- Rules chosen:
  - Approve is a conditional update (only a Pending profile), so a repeat or a click on an active member does nothing. Reject deletes the `user` row (cascades the profile, password account and invite use) only if the profile is Pending, so an active member or the admin can never be deleted from here. A rejected person's slot is not given back (the link's count is untouched), as the PRD says.
  - There is no separate "revoke": a member whose link is revoked would get a fresh one the moment they open their Invite screen. Only "make a new link" exists. The new link carries over the old link's sign-up count, otherwise replacing a link would hand a member a fresh quota of 5 automatic approvals.
- Real problem found by tests: replacing a link twice in the same millisecond (two admin clicks) made both batches pass the "I revoked it" check and the second failed on the one-active-link rule. The new link is now inserted only when `changes() = 1` for the revoke just before it in the same batch, and a database refusal is treated as "already replaced". Exactly one new link results (integration test). Also, one admin per instance is a database rule, so my first test helper that made two admins failed; tests now share one.
- Tests: 29 integration (approve/reject incl. unknown ids, active members and the admin, email and username reusable after reject, slot not freed, oldest-first listing with inviter, replace link: old code dead, new works, count carried and enforced, people kept, same-moment double click, listing, quota accepted/refused values and that it changes real sign-up outcomes); 6 e2e at phone width (quota form message and saving, five filler sign-ups then a waiting person appears with their email and inviter, cannot sign in until approved, approve then sign in works, reject asks then deletes and the details stop working, replaced link shows "Invite link not valid", member and signed-out visitors get 404 on all three pages, Settings row only for admin, no sideways scroll on a phone). The e2e file never changes the quota away from its default because other specs depend on it.
- Test slips fixed (not weakened): locators matched the Next route announcer's `alert` and the Approve button's label (use exact names).
- Open: no email to the invitee on approve or reject (needs the Resend slice), no admin email when someone is waiting, no search or paging on Approvals (first 200 shown), no way to see rejected history (by design: nothing is kept), no `test:a11y` run on the new screens (that suite does not exist yet).
