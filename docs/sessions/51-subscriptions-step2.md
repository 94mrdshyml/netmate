- What Polar's own API description says (downloaded `https://polar.sh/docs/openapi/2026-10.openapi.json` and read the exact fields, not the prose pages): a Subscription has `id`, `status` (incomplete, incomplete_expired, trialing, active, past_due, canceled, unpaid, paused), `amount`, `currency`, `cancel_at_period_end`, `current_period_end`, `modified_at` (may be null), `metadata`. An Order has `status` (draft, pending, paid, refunded, partially_refunded, void), `net_amount` (after discounts, before tax), `refunded_amount`, `billing_reason` (purchase, subscription_create, subscription_cycle, subscription_update, subscription_meter_cycle), `subscription_id` and the whole `subscription` object. The checkout's `metadata` is copied to the subscription and/or order; `POST /v1/checkouts/` takes `products`, `external_customer_id`, `metadata`, `success_url` (with `{CHECKOUT_ID}`) and `return_url`; `POST /v1/products/` takes a recurring month interval and a fixed USD price in cents; `PATCH /v1/subscriptions/{id}` with `cancel_at_period_end` stops it at the end of the period. Product `visibility` can be `private`.

- A flaky existing test, and what it turned out to be: `hq-branding` ("a logo and favicon ...") failed in 3 of 4 full local runs once my new browser test ran next to it, because the tab icon at `/brand-icon` still showed the name "Riverbank" that an earlier test had set and put back. I added temporary markers to find out why. The copy of the server that answered had never heard of any save (its "clear" count was zero), so saves and icon requests were being handled by different copies of the server (isolates) once the machine was busy. The settings cache is per copy by design ("other isolates catch up within 30 seconds", PRD), so a rename can lag in a busy copy. I did not change the test. The icon route now reads the live settings (one read; browsers keep the icon for five minutes), so a rename shows in the tab icon at once. Other pages still follow the 30 second rule.
