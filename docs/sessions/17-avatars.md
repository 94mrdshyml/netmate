# 17. Avatars and cover pictures (2026-10-23)
- Branch / PR: feat/avatars
- Before this: PR #33 (profiles, follows, Settings, bottom bar) is live, deploy green.
- Decision (owner): add DiceBear with permissive styles only. `@dicebear/core` and eight style packages are pinned at 9.4.2; each style's artwork was checked in code: CC0 for all eight (`initials thumbs shapes identicon rings glass pixel-art-neutral notionists-neutral`); `icons` (MIT, Bootstrap authors) was added then removed to keep the list CC0. The setup style list shrank from 9 to these 8 (the old `lorelei`, `notionists` and `bottts` are gone; a stored unknown style falls back to Initials, so the live instance cannot break). Worker size after the change: 1.9 MiB gzipped (limit 10 MiB on Paid).
- Done: default avatars drawn in the app at `/avatar/[userId]` (seeded by account id; Initials seeded by name so it can draw letters; cached 5 minutes; sandboxed headers). Uploads: `POST /api/upload` (session, same-site check, 30 per 10 minutes, size, first-byte sniff, then R2). Avatar up to 2 MB under `avatars/<user>/<random>.<ext>`, cover up to 5 MB under `banners/...`; type comes from the file's own bytes (JPEG, PNG, GIF, WebP), never the name or claimed type. Two-step like the PRD: upload returns a key, Save attaches it after `isAttachable` re-checks (the key is this person's, for this purpose, still stored, within the limit, and really that image type). A replaced or removed picture's file is deleted afterwards. Pictures are served from `/media/...` (avatars, banners, posts prefixes only; images only; immutable cache; `nosniff`; `sandbox` CSP). Avatars now show on posts, profiles, people lists and the edit form; the profile has a 3 to 1 cover (or a flat tint).
- Tests: 26 new unit (image sniffing incl. SVG/HTML/WAV/truncated files, all styles render, deterministic, different people differ, name change keeps the picture, unknown style falls back, nothing in an SVG can fetch from outside), 18 new integration (upload rules, exact size limits, disguised files, `isAttachable` against other people's, wrong-purpose, forged and fake-content keys, replace/remove deleting files, unchanged-when-omitted, refusal leaves the rest unchanged), 8 new e2e at phone width (default loads with no request to any other site, upload and see it on profile and posts, 3 to 1 cover, serving headers, only picture folders served, bad file and too-big messages, remove, upload endpoint needs a session and refuses cross-site forms).
- Real problems found by tests: (1) the cover rendered 2.4 to 1 because the image's height attribute beat the aspect ratio (`height: auto` fixed it). (2) My "no web address in the SVG" test was too blunt (licence text in `<metadata>` is not a request); it now checks that nothing can fetch (no href, src, @import, external url()). (3) An e2e "anonymous" request context silently inherited the admin login (same trap as before); it now passes an empty storage state.
- Decisions: serving goes through the app route `/media` for now; the media subdomain from the PRD replaces it later. No image resizing (the Worker has no image library): only byte limits and CSS cropping. Orphaned uploads (picked but never saved) stay in R2 until a clean-up job exists. Reserved usernames gained `avatar` and `media`.
- Open: no clean-up of orphaned uploads; no downscaling of big photos (a 2 MB avatar is loaded at full size); post pictures (4 per post) reuse this upload path in a later PR; hq will let the admin change the default style; logo and favicon upload.
